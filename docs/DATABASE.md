# Database

PostgreSQL via Drizzle ORM. Schema: `src/db/schema.ts`. Migrations: `drizzle/`.

- `0000_initial_schema.sql` — tables, constraints, indexes (generated by drizzle-kit).
- `0001_row_level_security.sql` — the restricted `aceap_app` role, identity
  helper functions, grants and row-level-security policies (hand-written).
- `0002_account_lifecycle.sql` — `password_reset_tokens`, `email_outbox` (generated).
- `0003_account_lifecycle_rls.sql` — RLS on for both, no grants to `aceap_app`
  (service-only tables; hand-written).
- `0004_lms_roster_proposals.sql` — `lms_roster_proposals`, the Canvas roster
  review snapshot (generated; FKs cascade from the class, the connection and users).
- `0005_lms_roster_proposals_rls.sql` — RLS on, no grants to `aceap_app`
  (service-only; hand-written).

Locally the database is embedded PGlite in `.data/pglite` (migrations apply
automatically on first open). With `DATABASE_URL` set, run `npm run db:migrate`.
New migrations: edit `schema.ts`, then `npx drizzle-kit generate`.

## Conventions

- Shared curriculum/content uses stable text ids (`calculus-ab.chain-trig`), so
  content sync is idempotent. Private records use UUIDs.
- Evidence tables denormalise `course_id` so RLS can scope a teacher to the
  course they teach.
- Observations are append-only (`question_responses`, `mastery_evidence`,
  `mastery_snapshots`, `learning_events`, `audit_logs`, `sync_logs`); projections
  (`mastery_states`, `activity_aggregates`) are rebuildable.
- Idempotency: `question_responses (user_id, idempotency_key)`,
  `mastery_evidence (response_id, skill_id)`, `learning_events (user_id, idempotency_key)`,
  `sync_jobs (idempotency_key)` are unique.

## Row-level security

Application code runs as the table owner and calls `asUser(actor, fn)` for
student-private reads; inside, the transaction executes
`SET LOCAL ROLE aceap_app` with `app.user_id` / `app.user_role` bound via
`set_config(..., true)` (transaction-local, so identity cannot leak across
pooled connections).

`aceap_app` can read shared curriculum, but never `users.password_hash`,
`sessions`, `password_reset_tokens`, `email_outbox`, `lms_roster_proposals`, `question_versions`
(answer keys) or `application_settings`, and
has no write access to evidence or mastery tables. Highlights:

| Data | Visible to |
|---|---|
| attempts, responses, evidence, mastery, snapshots, misconceptions, reviews, lesson progress, activity, events | the student; staff (teacher, or school admin of the org) of an **active, non-archived class the student is enrolled in, for that class's course only**; platform admins |
| classes, enrolments, assignments, submissions, gradebook entries | class staff and enrolled students (assignments only when targeted to them) |
| vault notes and links | the owner; a teacher only via an explicit `vault_shares` row for a class they teach — **no admin override** |
| organisations, LMS connections, sync jobs | organisation staff; platform admins |
| audit logs | org staff for their org; platform admins |

Tests: `tests/authorization.test.ts` asserts these at the database level.

## Retention

### What is automated (`npm run retention`)

`src/modules/accounts/retention.ts`, run by `scripts/retention.ts`. A plain
`npm run retention` is a **dry run** that prints how many rows each rule would
delete; `npm run retention -- --apply` deletes them and writes a
`retention.applied` audit row with the counts (`--json` for machine-readable
output). It is idempotent and exits non-zero on failure.

| Rule | Deleted |
|---|---|
| Sessions | expired rows (`expires_at` < now) — also pruned on every sign-in |
| Password-reset tokens | used or expired more than 7 days ago |
| Dev email outbox | messages older than 30 days |
| Canvas roster review proposals | `lms_roster_proposals` rows older than 30 days (`rosterProposals`); each review also replaces the class's previous snapshot, and class/connection deletion cascades |
| Raw engagement telemetry | `learning_events` and `learning_sessions` older than `RETENTION_EVENTS_DAYS` (default 730; values under 30 are ignored). `activity_aggregates` (daily rollups) are kept |
| Deleted accounts | accounts soft-deleted more than `ACCOUNT_PURGE_GRACE_DAYS` ago (default 30) are hard-deleted by `purgeDeletedAccounts()` — see below |

**Never deleted by retention:** `mastery_evidence`, `question_responses`,
`mastery_snapshots`, `mastery_states`, `attempts`, vault notes. They are the
student's learning record, kept while the account exists and exportable by the
student (`/app/vault/export`). Tested in `tests/account-lifecycle.test.ts`.

**Account deletion and purge.** Self-service deletion
(`src/modules/accounts/deletion.ts`) soft-deletes (`users.deleted_at`), revokes
all sessions, sets class enrolments to `removed` and deletes LMS identity
mappings immediately. After the grace period the purge deletes the `users` row;
foreign keys cascade to every private record (attempts, responses, evidence,
mastery, snapshots, events, sessions, vault notes, submissions, gradebook rows,
AI usage, reset tokens). Pending `sync_jobs` for the student (no FK) are deleted
explicitly, and a teacher's empty personal organisation is removed. `audit_logs`
rows are kept: they contain only uuids (no names or emails — asserted in tests),
which no longer resolve to a person. Teachers who own classes or authored
assignments cannot self-delete (the purge also skips and reports them).

### Scheduling

Run `npm run retention -- --apply` once a day with the production environment
(`DATABASE_URL` set), e.g.:

- cron: `15 3 * * * cd /srv/aceap && npm run retention -- --apply >> /var/log/aceap-retention.log 2>&1`
- a platform scheduler (Vercel Cron / Render cron job / Fly machine schedule /
  Kubernetes `CronJob`) running the same command, or a scheduled CI job.

Alert on a non-zero exit. With embedded PGlite (single process) stop the app
first or run it from the app host's maintenance window.

### Still requires a school agreement

The windows above are defaults, not commitments. A data-processing agreement
with each school/district should fix: the telemetry window (proposed: the
enrolment plus one school year), how long evidence/mastery is kept after a
student leaves a school (today: as long as the account exists), audit-log
retention (proposed 3 years — **not enforced by code yet**), the deletion grace
period, whether schools (not only students) can request deletion of a student
account, and export of class gradebooks before a student's purge removes their
rows. See SECURITY.md.

## Recovery

- Mastery projection: `rebuildMastery()` (see MASTERY_ENGINE.md §10).
- Activity aggregates can be recomputed from `learning_sessions`.
- Curriculum/content: `npm run content:sync` from the files in `content/`.
